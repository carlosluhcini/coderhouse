# Nube Clara: procedimiento de despliegue

Este manual describe una plataforma ficticia de entrenamiento llamada Nube Clara. Sus comandos y sus reglas son ejemplos educativos; no corresponden a herramientas comerciales ni a instrucciones para un sistema real. El alcance del manual es la operación de microservicios de una aplicación de reservas. No documenta otros productos ni servicios externos.

La aplicación de reservas contiene los módulos agenda, clientes, notificaciones y pagos de prueba. Cada módulo tiene un repositorio y una imagen de contenedor propios. La versión se identifica mediante una etiqueta inmutable de imagen. El operador puede desplegar agenda sin volver a publicar clientes. Las dependencias se comunican mediante contratos HTTP versionados, por lo que un cambio compatible no obliga a una entrega conjunta. Antes de liberar una imagen se verifica la compatibilidad de esos contratos.

El flujo obligatorio de publicación contiene cuatro etapas: validación, construcción, prueba en ensayo y promoción. La validación ejecuta pruebas unitarias y comprueba el formato del código. La construcción genera una imagen y registra su huella digital. La prueba en ensayo utiliza datos sintéticos y comprueba el endpoint de salud. La promoción toma exactamente la imagen ya probada; no se recompila para producción. Una compilación nueva necesita repetir el proceso completo.

Para iniciar una promoción, el operador registra en el ticket el módulo, la etiqueta de imagen, la huella digital y la persona que aprobó la prueba. La orden ficticia es nc promote --module agenda --image etiqueta. El estado inicial de la promoción es pendiente. Cuando todas las instancias nuevas responden correctamente, el estado pasa a disponible. El servicio de enrutamiento continúa enviando tráfico a las instancias anteriores mientras las nuevas se preparan.

La preparación comprueba conectividad con las dependencias, disponibilidad de configuración y acceso a los secretos necesarios. El endpoint /ready devuelve 200 solo cuando la instancia puede recibir solicitudes. El endpoint /live informa si el proceso está en ejecución. Una respuesta de /live no demuestra que el servicio esté preparado; por eso no debe reemplazar la comprobación de /ready. La evaluación de promoción consulta ambos endpoints y registra sus resultados.

La promoción se realiza en horario de acompañamiento del equipo. Durante los primeros minutos el operador observa errores, latencia y uso de recursos. Si una comprobación falla, se interrumpe la promoción y se revisa el procedimiento de recuperación. El objetivo del entrenamiento es aprender a liberar componentes de forma independiente y trazable, manteniendo la posibilidad de regresar a una versión anterior. Las credenciales nunca se escriben en el ticket ni en los logs.
