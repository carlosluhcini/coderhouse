# Nube Clara: métricas y observabilidad

Este apunte describe las señales de operación de la plataforma ficticia Nube Clara. El tablero de laboratorio muestra disponibilidad, latencia, tasa de errores y saturación de recursos para cada microservicio. Las mediciones se separan por módulo y por versión, de modo que sea posible comparar una imagen nueva con la revisión anterior. Una cifra global de la aplicación no reemplaza la revisión de las señales del módulo que está cambiando.

El identificador de correlación vincula los eventos de una solicitud. El primer servicio asigna el campo trace_id y los módulos siguientes lo conservan. Los logs incluyen hora UTC, módulo, revisión, nivel del evento y trace_id. No deben incluir contraseñas, tokens, claves de API ni información personal de clientes. Los ejemplos del laboratorio utilizan nombres ficticios y reservas sintéticas para que puedan compartirse durante las prácticas sin exponer datos reales.

La latencia se informa mediante percentiles. El percentil 95 representa el tiempo que no supera el 95 por ciento de las solicitudes observadas durante la ventana de medición. El tablero usa una ventana de cinco minutos. Una media baja puede ocultar solicitudes muy lentas, por lo que el operador revisa el percentil junto con el volumen de tráfico. En un módulo sin solicitudes recientes, la ausencia de datos no demuestra que el servicio funcione correctamente.

La alerta de errores del laboratorio se activa cuando la tasa de respuestas fallidas supera el cinco por ciento durante tres minutos consecutivos. La alerta se identifica como ERRORES_SOSTENIDOS. Antes de decidir una acción, el operador confirma el volumen de solicitudes y consulta los eventos recientes. Un fallo aislado con poco tráfico puede cambiar el porcentaje de manera importante y necesita interpretación. La alerta es una señal para investigar, no una orden automática de reinicio.

La saturación se observa mediante uso de CPU, memoria y longitud de colas. Si crece la cola de notificaciones, se revisa primero si los consumidores están activos. Si las instancias están listas pero el procesamiento sigue atrasado, se compara el ritmo de ingreso con la capacidad de consumo. Escalar un servicio no corrige mensajes inválidos ni errores de lógica. Esos casos se registran como incidentes de aplicación y necesitan una corrección de código.

Cada incidente tiene una línea de tiempo que reúne promociones, alertas y decisiones. Al cerrar el incidente se conserva el síntoma, la causa confirmada y la acción que restauró el servicio. Una hipótesis no verificada debe quedar identificada como hipótesis. La finalidad de la observabilidad es aportar evidencia para operar y aprender; no permite deducir datos de negocio ausentes en el corpus, como precios comerciales o resultados de eventos deportivos.
